# SQL学習用Webアプリ 引継ぎ資料

## 0. この資料の位置づけ
この資料は、後任者が全体像を素早く把握できるよう整理した引継ぎ用メモである。  

---

## 1. アプリの概要
本アプリは、**SQL初学者向けの学習支援Webアプリ**であり、以下の流れで学べる構成になっている。

- 学習ページ
- 実行例ページ
- 演習ページ
- クイズページ

単なる解説サイトではなく、**ユーザーごとの専用DBを用意し、SQLを実際に実行させる**ことが大きな特徴である。  
特に、`DELETE`、`UPDATE`、`INSERT`、`JOIN`、`GROUP BY`、`トランザクション` など、**実データを触りながら学ぶ**形になっている。

---

## 2. 想定技術スタック
コードから確認できる範囲では、以下の構成になっている。

- バックエンド: Flask
- DB接続: `mysql.connector`
- 認証補助: `flask_bcrypt`
- 設定読み込み: `Config`
- 独自DBラッパー: `DataStore.MySQL`
- フロント: Jinja2 テンプレート + CSS

### 補足
`app.py` 内では以下の3種類の接続情報を使い分けている。

- `dns`: 共通学習用DB（`dataset`）
- `user_dns`: ユーザー管理用DB（`user_info`）
- `this_users_dns`: ログイン中ユーザー専用DB（`*_db` を後から設定）

## 3. DB構成の考え方
### 3.1 共通DB
`dataset` は、教材用の初期データを持つ共通DBとして扱われている。  
各種テーブル（例: `users`, `products`, `employees`, `sales`, `accounts` など）の**元データ置き場**である。

### 3.2 ユーザー管理DB
`user_info` は、以下のような用途を持つ。

- ログインユーザー情報の保持
- 管理用情報の保持
- ユーザーIDと専用DB名の対応付け

### 3.3 ユーザー専用DB
サインアップ時に `username_db` を作成し、`dataset` から必要テーブルをコピーしている。  
この構成により、**学習者ごとにDB状態を独立**させている。

## 4. 認証・ユーザー管理
### 4.1 ログイン制御
`before_request` で、`/login` と `/signup` 以外はログイン必須になっている。  
静的ファイル `/static` も例外扱い。

### 4.2 サインアップ
サインアップ時の流れは以下。

1. `user_info.users` を確認して重複ユーザー名をチェック
2. パスワードをハッシュ化
3. `user_info.users` に登録
4. `username_db` を新規作成
5. `dataset` から各学習用テーブルをコピー
6. `user_databases` にユーザーIDとDB名を保存

### 4.3 ログイン
ログイン成功時は以下を `session` に保持する。

- `user_id`
- `username`
- `is_admin`

さらに、`this_users_dns['database']` に `username_db` をセットし、以降の学習SQLはそのDBへ接続する。

### 4.4 管理者機能
`admin_required` デコレータにより、管理者のみ以下へアクセス可能。

- ユーザー一覧
- ユーザー削除
- ユーザー進捗確認

## 6. 実装上の重要関数

### 6.1 `fetch_table_data(table_name)`
役割:
- 指定テーブルの `DESC`
- 指定テーブルの `SELECT *`

を実行して、表示用データをまとめて返す。  
多くの演習ページで共通利用されている。

### 6.2 `initialize_table(table_name, user_dns)`
役割:
- ユーザー専用DB上の対象テーブルを削除
- `dataset` から構造をコピー
- `dataset` からデータをコピー

**「初期状態に戻す」ボタンの中核**になっている。

### 6.3 `create_backup_table(table_name)` / `create_backup(table_name)`
役割:
- 更新前のテーブルを `*_backup` として退避

`UPDATE` 系のロールバックや「1つ前の状態に戻す」用途で使われる。

### 6.4 `safe_exec_sql(sql, allowed_tables=None, commit=False, db_config=None)`
役割:
- 危険なSQLを弾いた上で実行する安全ラッパー

現状のチェック内容:
- 空SQLの拒否
- セミコロンの拒否
- コメントの拒否 (`--`, `/* */`)
- 危険キーワードの拒否 (`drop`, `truncate`, `alter`, `grant`, `revoke`, `create`, `shutdown`, `use`, `set password`)
- システムスキーマ参照の拒否
- 現状は **DELETE文のみ許可**

この関数は、旧実装の単純な文字列連結SQLより安全性が高く、今後の標準化対象として重要。

### 6.5 `diff_table(before, after)`
役割:
- 実行前後テーブルの差分比較
- 変更セル、追加行、削除行を判定

トランザクション学習や差分表示に関わる重要関数。

## 7. トランザクション機能のポイント
### 7.1 基本操作演習
`/transaction/basic-operations/practice` では、以下を体験できる。

- 初期化
- START TRANSACTION
- SQL実行
- COMMIT
- ROLLBACK

実装上は `active_connections` という辞書に接続を保持し、`session['conn_id']` と紐づけて扱っている。  
また、`sql_history` をセッションに持ち、履歴表示もしている。

### 7.2 Isolation 演習
`/transaction/acid/isolation/practice` では、Lost Update を疑似的に見せる仕組みが入っている。

- `simulate_conflict`: 競合が起きた場合の期待値と崩れた結果を比較
- `simulate_isolation`: 実際に順番に更新して Isolation の効果を体験

教育的にはかなり良い題材になっている。

## 8. DELETE 学習の実装メモ
### 8.1 学習ページ
`delete_multiple_study.html` は、`DELETE` の複数条件版の学習ページ。  
内容は以下のような構成。

- 複数条件削除の説明
- 基本構文 (`AND`, `OR`)
- 使用例
- `AND` / `OR` 混在時の括弧利用に関する注意
- 前へ / 次へ ナビゲーション

### 8.2 演習ページ
`/basic/delete/<type>/practice` で `single` と `multiple` を切り替えている。  
対象テーブルは `employees` 固定。

### 8.3 共通タプル削除
`/basic/delete/shared-tuple/practice/<mode>` では DELETE JOIN を扱う。  
こちらは `safe_exec_sql()` を利用しており、旧来の `exec_sql()` 直実行より安全性が高い。

## 10. 既知の懸念点・技術的負債
以下は、今後の保守で特に注意したいポイント。

### 10.1 `app.py` が巨大で責務が集中している
1ファイルに以下が混在している。

- 認証
- ユーザー管理
- 学習ページ
- 演習ページ
- クイズ
- トランザクション
- DBユーティリティ
- 差分表示ロジック

今後の保守性を考えると、Blueprint や機能単位の分割が望ましい。

### 10.2 旧実装では SQL 文字列連結が多い
一部の検索・削除・JOIN・認証周辺で、フォーム入力をそのまま SQL に連結している箇所がある。  
安全性の観点では、`safe_exec_sql()` やプレースホルダ利用への移行が必要。

### 10.3 コメントと実装が一致していない箇所がある
例として、ログイン処理では「パラメータ化されたクエリ」とコメントされているが、実際は文字列連結になっている。  
この種のズレは保守者を誤解させるため、優先的に是正したい。

### 10.4 `SECRET_KEY` が起動時ランダム生成
`os.urandom(24)` を毎回設定しているため、再起動時のセッション互換性に注意が必要。  
本番運用では固定設定（環境変数等）に寄せた方が扱いやすい。

### 10.5 `this_users_dns` がグローバル可変
ログイン時に `this_users_dns['database']` を書き換える構造のため、**同時アクセス時の安全性**は要確認。  
開発用途・単純運用なら動くが、マルチユーザー環境では注意。

### 10.6 `active_connections` もグローバル辞書
トランザクション演習用に接続を保持しているが、複数プロセス・複数ワーカー構成では扱いが難しくなる可能性がある。

### 10.7 CSS の定義重複がある
`style.css` 内で同名クラスが複数回出てくる箇所がある。  
現状は「後勝ち」で動くが、将来の修正で見た目が崩れるリスクあり。

## 14. 一言まとめ
このアプリは、**SQLを「読む」だけでなく「実行して学ぶ」ための教材アプリ**としてよく作り込まれている。  
特に、

- ユーザー専用DBの自動生成
- 初期化 / バックアップ / ロールバック
- トランザクション学習
- 差分表示

あたりは強みである。  
一方で、保守面では **巨大な `app.py`、旧式のSQL連結、グローバル状態への依存** が大きな課題である。  
後任者はまず **安全性の整理と責務分割** から着手すると進めやすい。

> 私自身，この整理が不十分なまま進めてしまい，後から方針を見直すことになった．

2. 作る機能を絞る
- ALTER文
- TRANSACTION

> 今後はこれらを主軸として開発するのがよいと考える．
> これらは既存の学習サービスで十分に扱われていないことが多く，本アプリの独自性を出しやすい．

3. SQLインジェクション対策を軽視しない
> SQLをWeb上で実行させるアプリでは，SQLインジェクション対策は特に重要である．
> 安全性の確保は実装上の課題であるだけでなく，研究上の重要な論点にもなり得る．
> 私自身，この点を後から重く認識したため，早い段階で方針に含めておくことを勧める．

> 樋口研では論文を大量に読むことが必須という雰囲気ではないかもしれないが，
